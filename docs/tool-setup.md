# Tool setup

A specialist records the capabilities its work requires. Each capability states why it matters, the inputs and outputs, required access, setup steps, and the observation that verifies it.

## Readiness states

| State | Meaning |
|---|---|
| `available` | The package records an available capability and its verification requirement. |
| `configurable` | The host has an integration that needs configuration. |
| `build-required` | The selected work needs additional implementation. |
| `missing` | The required capability is unavailable in the current setup. |

Readiness is a recorded assessment. An observed tool result establishes the operation actually exercised. Each result retains its input, time, target, and stated limits.

## Setup records

A setup plan identifies the specific tool, required version or license, intended records, permitted paths or endpoints, access needs, configuration, and verification. The host governs permissions and credentials.

For Grant Operations, setup can combine a source library, an opportunity screener and an application-evidence register. Verification uses a fictional packet and independently specified program criteria. Tests exercise monetary boundaries, missing evidence, expired dates and distinctions between reported facts and verified organizational records.

For Drone Shoot Operations, a capability plan can cover jurisdiction-specific research, weather and airspace information, equipment records and a shoot checklist. Each integration records its information source, time, location, coverage and required human decisions. Verification can use a fictional shoot to check missing records, conflicting conditions and the escalation path. Current flight authorization requires its applicable evidence and permissions.

## Native profile delivery

Adeptory prepares the specialist's instructions and library as a local Hermes profile distribution. The host installs the distribution. Adeptory checks the installed starter identity, refreshes plugin exposure through the public CLI, and requires an observed ordinary task in the new profile.

Model and provider selection can travel with the distribution as non-secret configuration. Credential setup remains with Hermes. A completed profile retains the source qualifications and unresolved applicability conditions that govern later work.

## Failures and fallbacks

A setup failure records the affected capability, the observed error, and the next action. Independent construction tasks can continue. A fallback describes the evidence it can supply and the conclusions that evidence supports. The build's completion status reflects required capabilities and their recorded verification.

## Continuing capability development

The specialist's library contains `capability-roadmap.json` and `capability-roadmap.md`. Both derive from the package's capability records. The navigation index links the readable roadmap, and profile exports include it with the specialist instructions.

The roadmap separates recorded available capabilities from work to configure, build or acquire. Each record states why the capability helps, its inputs and outputs, the access it needs, setup work and a verification method. Readiness remains a recorded assessment. A claim that a capability is verified requires an observed test result retained in the library.

During later tasks, the specialist can add useful capabilities, build authorized improvements and compare their results with independent expected evidence. It preserves working capabilities and retains unsuccessful work with a next action. Future improvements can remain planned while the initial specialist delivers its selected work.

An adopted specialist created from the user's build request keeps ordinary-use authorization across revisions within its existing goal, subject and scope. Changes to that mission reopen adoption. New unknown business choices stay unresolved. A source revision still marks affected knowledge for review, and the host continues to govern tool access and consequential actions.
